它解决什么

读一个陌生仓库，最费时间的不是读代码，是搞清楚从哪进、谁调谁、哪里会炸。 模型一次读不完大仓库，硬塞进去就会开始编。RepoSleuth 把这件事拆开： 先选对仓库，再分头读，最后交叉核对，产出一份能直接看的报告。

输出三样东西：mermaid 架构图、新人上手路线、风险预警清单。

流水线

谁在干活

  • Scout：把模糊需求变成确定的仓库。GitHub 搜索后重排，Top1 达到阈值就直接用，否则把候选交给人选——避免猜错仓库后一路错到底。
  • Cartographer：读目录、依赖和构建文件，画模块关系，输出 mermaid。
  • Reader：找入口、配置和启动命令，写一条新人能照着走的上手路线。
  • Auditor：查过期依赖、缺失配置、凭据泄露、缺失的 CI，按严重程度排序。
  • Chief：汇总三份结论，处理互相矛盾的地方，最后成文。

几个关键决定

编排交给状态机LangGraph / 可定位

一次分析有固定阶段：解析需求、检索选库、三代理并行、主笔。写成状态机的理由是每一步的 输入输出都是显式的：出错能定位到具体节点，也能只重跑某一段，而不是从头再烧一遍 token。

工具层做成无状态 MCP Server边界 / 复用

检索、clone、建索引、扫风险、读文件都封装成 MCP 工具，和编排层分开。 这样同一套工具既能被 CLI 调，也能被 Claude、Cursor 直接挂载；服务本身不存会话， 水平扩展不用考虑粘性。

选错仓库比选不出更贵检索 / 确定性

模糊需求先做 GitHub 搜索，再对候选重排。只有 Top1 相似度达到阈值才自动选定， 否则把候选做成卡片让人点。自动化少一点，换掉的是「分析了半天、分析错仓库」这种最贵的事故。

测试不碰网络，也不碰真模型测试 / 防退化

单测用假的 chat model 替换 LLM，用本地模板仓库替换 GitHub；另外拿两个真实仓库 （pallets/click、httpie/cli）当基线。prompt 或检索逻辑改动后跑一遍， 防止报告质量悄悄退化——这类系统最怕的不是报错，是「看起来还行」。

工程细节

  • 网页端是 FastAPI + SSE：检索、精读、三个 Agent 的阶段事件实时推到页面，最后渲染 mermaid。
  • Gradio 单页保留人工确认环节，候选仓库和最终报告都能在页面上改。
  • 模型可换：默认 glm-4-flash（免费额度），也支持 deepseek-chat、qwen 等 OpenAI 兼容接口。
  • CLI 与网页共用同一条流水线和同一个报告渲染层，输出保持一份格式。
  • 五个 MCP 工具：github_search、clone_repo、repo_map、risk_scan、ingest_repo。
